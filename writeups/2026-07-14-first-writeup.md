# Building Atlas: A RAG-Based Document Q&A Platform with OCR Fallback

## Summary

Atlas is a full-stack web application that lets users upload PDF and TXT documents, search them semantically, and ask questions about their contents through a chat interface. The system uses Retrieval-Augmented Generation (RAG) to answer from document context when relevant chunks are found, falling back to the LLM's general knowledge otherwise. Scanned PDFs with no extractable text are handled via an OCR pipeline using Tesseract.js. The stack is React + Vite on the frontend, Express.js on the backend, Neon PostgreSQL with pgvector for vector search, and Groq for LLM generation.

## Problem

Users have personal documents — resumes, notes, contracts, ebooks — and want to ask questions about them without manually reading through everything. Existing solutions either require sending documents to third-party services or lack citation support so users can't verify where answers come from. The specific requirements were:

1. Upload PDF and TXT files and get them into a searchable form automatically
2. Search across document contents using natural language, not keyword matching
3. Chat about documents with answers that cite specific source chunks
4. Handle scanned PDFs that have no machine-readable text
5. Run without an expensive GPU or complex infrastructure

## Investigation

The initial investigation focused on three areas: vector search, LLM generation, and OCR.

For vector search, pgvector was the obvious choice because the project already targeted PostgreSQL for data storage. Running a separate vector database (Pinecone, Weaviate, Qdrant) would add operational complexity and network latency for no benefit at this scale. The 384-dimensional BAAI/bge-small-en-v1.5 model was chosen for embeddings because it works well with the HuggingFace Inference API — no need to host a model server.

For LLM generation, Groq was selected because it provides fast inference through a simple OpenAI-compatible REST API. The application needed both synchronous generation (for the standalone Q&A endpoint) and streaming (for the chat interface). Groq supports both through the same `/chat/completions` endpoint with a `stream` flag.

For OCR, the architecture went through two revisions. The initial design specified `pdfjs-dist + sharp` for PDF rendering. During the engineering review, sharp was dropped in favor of `@napi-rs/canvas` because the latter can produce PNG buffers directly from pdfjs-dist's canvas context, eliminating one native dependency and reducing peak memory by ~30-50MB. The key constraint was Railway's 512MB memory limit, which meant every megabyte counted.

## Implementation

The implementation spanned six milestones over three weeks, tracked in separate git branches.

### Milestone 1-2: Document Upload and Chunking

The upload endpoint accepts PDF and TXT files via Multer with a 25MB limit. Files are validated by MIME type and extension, then written to a local `uploads/` directory with a UUID prefix to prevent collisions. Text extraction uses `pdf-parse` for PDFs and direct UTF-8 decoding for TXT files.

The chunking service splits extracted text into 500-character windows with 100-character overlap. This is deliberately simple — no sentence boundary detection, no NLP. The overlap ensures that term boundaries near the cut point appear in at least one chunk, which is important for retrieval quality. Each chunk is stored in the `chunks` table with a sequential index and foreign key to its parent document.

### Milestone 3: Embeddings and pgvector

Each chunk gets a vector(384) embedding generated by the HuggingFace Inference API using BAAI/bge-small-en-v1.5. The embedding provider is abstracted behind an interface (`EmbeddingProvider`) with one working implementation (HuggingFace) and one stub (LocalTransformers, marked "not implemented yet").

The pgvector extension powers the HNSW index on the embedding column using cosine distance. Queries are embedded with the same model, then the index returns the top-K nearest neighbors above a similarity threshold (default 0.50).

### Milestone 4-5: Ingestion Pipeline and Retrieval

The ingestion pipeline is fire-and-forget — the upload endpoint returns HTTP 201 immediately, and `processDocument` runs asynchronously. The pipeline is sequential: extracting (30%) -> chunking (60%) -> embedding (90%) -> ready (100%). Each stage updates the document's status and progress in the database. The frontend polls every 2 seconds (backing off to 10) with a 10-minute timeout.

The retrieval layer wraps the search service with conversation-scoped filtering. When a chat query arrives, only chunks from documents attached to that conversation are searched. This prevents context leakage between conversations.

### Milestone 6: OCR Fallback

The OCR pipeline is triggered only when two conditions are met: the file is a PDF, and `pdf-parse` returns fewer than 50 characters of text. This avoids running OCR on text PDFs, which would be 10-100x slower with worse output.

When triggered, the pipeline:
1. Renders PDF pages to PNG via `pdfjs-dist` with a custom `NapiCanvasFactory` (using `@napi-rs/canvas` instead of `node-canvas` to avoid native build dependencies)
2. Clamps render dimensions to 2560px max to prevent OOM from ultra-high-resolution pages
3. Runs Tesseract.js OCR sequentially across pages (max 10 pages, ~3-7 seconds per page)
4. Scores OCR quality using alpha ratio, average word length, dictionary match ratio, and printable character ratio

An in-process sequential queue prevents concurrent OCR jobs from exceeding Railway's 512MB memory. The queue has a max depth of 5 and a 300-second acquire timeout.

### Milestone 7: Streaming Chat and RAG

The chat endpoint uses Server-Sent Events for token streaming. The Groq provider's `generateStream()` method reads Groq's own SSE stream and yields tokens, which the Express route forwards to the client with a 15-second heartbeat.

The RAG routing decision uses two gates:
1. **Similarity gate**: the top retrieved chunk must have cosine similarity >= 0.50
2. **Overlap gate**: at least one query term of length >= 4 must appear in the retrieved chunk text

This dual gate prevents false positives from embedding-only retrieval. A query that is semantically close but lexically unrelated to any chunk will fall back to the LLM's general knowledge.

### Authentication

Better Auth handles email/password authentication with a permissive middleware pattern: the middleware populates `req.user` when a valid session cookie is present but does not reject unauthenticated requests. Individual route handlers decide whether auth is required. This allows gradual rollout of authenticated features and cleaner error handling.

## Architecture

The system is a monolith with in-process dependency injection. All module wiring happens in `server/app.js`, which reads like a dependency graph:

```
app.js
  ├── generationConfig (env-based: model, temperature, topK)
  ├── storageProvider (LocalStorageProvider -> uploads/)
  ├── pool (PostgreSQL connection)
  ├── documentsRepository
  ├── chunkRepository
  ├── embeddingRepository
  ├── conversationRepository
  ├── conversationDocumentRepository
  ├── searchRepository
  ├── chunkService (text splitting)
  ├── documentOrchestrator (pipeline orchestrator)
  ├── embeddingProvider (HuggingFace or LocalTransformers)
  ├── embeddingService (batch embedding)
  ├── searchService (query embedding + vector search)
  ├── retrievalService (conversation-scoped search)
  ├── generationProvider (Groq)
  ├── generationService (RAG routing + prompt building)
  └── chatService (conversation management + streaming)
```

Each module exports a factory function that receives its dependencies explicitly. There are no global singletons, no service locators, and no circular dependencies.

An architecture diagram should show:
- Browser -> Vite (dev proxy) -> Express (REST + SSE)
- Express routes -> auth middleware -> service modules -> repository layer -> PostgreSQL
- Document pipeline as a separate async flow: upload -> file write -> DB insert -> fire-and-forget processDocument
- OCR as a sub-pipeline within processDocument, gated by a 50-character threshold
- Groq and HuggingFace as external API dependencies
- Vercel for frontend static hosting, Railway for backend process

## Challenges

### Railway Memory Limits

The 512MB memory limit on Railway's hobby tier was the most significant constraint. Two concurrent OCR jobs would exceed available memory. The solution was a sequential in-process queue with a max depth of 5. The queue uses a simple mutex lock with a FIFO callback array — no Redis, no BullMQ, just a `lockAcquired` boolean and a `queue` array.

The queue lock must be released in a `finally` block. If a crash happens between acquire and release, the in-memory lock is lost (the process dies), but the startup reconciliation fails any document stuck in a processing state for more than 30 minutes.

### Start-up Reconciliation

When the Node.js process crashes mid-OCR, the document is left in `ocr` status in the database. On restart, the status guard in `processDocument` skips it because it's already in a processing state. Without intervention, the document is stuck forever.

The solution is a startup reconciliation query that marks any document in `{extracting, ocr, chunking, embedding}` status with a `processing_started_at` older than 30 minutes as `failed`. This runs once when the server starts.

### pdfjs-dist Memory Management

pdfjs-dist is designed for browser use where page objects are garbage-collected when the user navigates away. In a long-running Node.js process, each `PDFDocumentProxy` holds ~50-100MB of parsed PDF structure, and each `PDFPageProxy` holds rendered bitmap data. Without explicit cleanup, memory grows linearly with each OCR'd document.

The fix is `page.cleanup()` after each page and `doc.destroy()` after all pages, both in `finally` blocks.

## Trade-offs

### In-Process Queue vs. External Queue

The sequential OCR queue is in-process — it does not survive process crashes. An external queue (Bull with Redis) would persist jobs across restarts and enable multi-instance deployments. The trade-off was accepted because Atlas runs as a single process on Railway, Redis adds operational cost, and the startup reconciliation handles the crash case.

### Fixed-Window Chunking vs. Semantic Chunking

Chunking uses fixed 500-character windows with 100-character overlap. This is naive — it splits mid-sentence and mid-paragraph — but it is fast, deterministic, and requires no NLP model. Semantic chunking (sentence splitting, paragraph detection, section-boundary awareness) would produce better retrieval contexts but adds complexity. For v1, fixed windows are acceptable.

### SSE vs. WebSocket

Chat streaming uses SSE rather than WebSocket. SSE is simpler (no upgrade negotiation, works over standard HTTP/1.1, no special proxy configuration) and matches the use case — the client sends a single POST and receives a stream of tokens. The downside is no built-in reconnection; if the stream drops mid-response, the user must retry.

## Lessons Learned

1. **Memory budget first**: On constrained environments (512MB), plan peak memory before writing code. The OCR pipeline went through two revisions because the initial design didn't account for pdfjs-dist's memory footprint.

2. **Fire-and-forget needs recovery**: An async pipeline is elegant until the process dies. Always have a reconciliation mechanism for in-flight work.

3. **Permissionless middleware is worth the boilerplate**: The auth middleware populates `req.user` without rejecting requests. Each route handler decides if auth is required. This pattern made it easy to add authenticated features incrementally and keeps error handling local to each route.

4. **Abstract providers pay off late**: The `EmbeddingProvider`, `GenerationProvider`, and `StorageProvider` abstract classes were added early. They add boilerplate for the first implementation but make the second implementation trivial. The `LocalTransformersProvider` stub exists because the interface was defined before the second implementation was needed.

## Future Improvements

- **Multi-provider generation**: Only Groq is implemented. The `GenerationProvider` interface is defined and ready for OpenAI, Anthropic, or Together.
- **Local embeddings**: The `LocalTransformersProvider` is a stub. Once implemented, embedding generation would not require an external API.
- **Persistent job queue**: Replace the in-process OCR queue with Bull or similar for crash resilience and multi-instance support.
- **RAG threshold configuration**: The similarity (0.50) and overlap (>= 1) thresholds are hardcoded. Making them configurable via env vars or per-conversation settings would improve adaptability.
- **OCR language config**: Currently hardcoded to English. A configurable `OCR_LANGUAGE` env var would support multi-language documents.
- **Sentence-aware chunking**: Moving from fixed windows to sentence-boundary chunking would improve retrieval quality.
